# Likeback

A self-contained Cloudflare Pages Advanced Mode app or Worker (`likeback`) with a Japanese frontend, 20 categories, month/category/author filters, search, shuffle, personal PNG cards, and responsive masonry (up to five columns). Pages uses a shell-only copy step; Worker deployments need no build step. Both use the same bindings.

1. Enable OAuth 2.0 for a confidential Web App in the X developer portal. Register `https://likeback.kzyxyz16.workers.dev/callback` and the Worker origin `https://likeback.kzyxyz16.workers.dev` (or your deployed origin). OAuth callback URLs are derived from `new URL(request.url).origin`; shared links use the current page origin. Request `tweet.read users.read like.read offline.access` and access to liked tweets.
2. Run `wrangler kv namespace create SESSIONS --config wrangler.worker.toml`. Replace the existing example namespace `id` in both `wrangler.toml` and `wrangler.worker.toml` with your own ID. The checked-in ID is an example value, not a usable placeholder or secret.
3. Configure `X_CLIENT_ID`, `X_CLIENT_SECRET`, and `SESSION_SECRET` using `wrangler secret put <NAME> --config wrangler.worker.toml`. Generate a long random session secret, for example with `openssl rand -hex 32`. Use OAuth 2.0 credentials, not OAuth 1.0 API keys. Keep the existing `SESSIONS` KV and `AI` bindings.
4. Run `node --check src/worker.js`, preview with `wrangler dev --config wrangler.worker.toml`, then deploy with `wrangler deploy --config wrangler.worker.toml`. OAuth needs HTTPS because cookies are Secure.

To deploy on Cloudflare Pages:

1. Create a Pages project named `likeback`. For Git integration, select no framework, set the build command to `sh scripts/build-pages.sh`, and set the build output directory to `public`.
2. For a direct upload using an installed Wrangler CLI, run `sh scripts/build-pages.sh`, then `wrangler pages project create likeback` (once) and `wrangler pages deploy public --project-name likeback`. The build needs no npm or dependencies; it copies `src/worker.js` to the ignored `public/_worker.js`, which handles all routes in Advanced Mode.
3. In the Pages project's settings, add encrypted secrets `X_CLIENT_ID`, `X_CLIENT_SECRET`, and `SESSION_SECRET` for production and any previews you use, then redeploy. `wrangler.toml` supplies the `SESSIONS` KV and `AI` bindings; keep their values aligned with `wrangler.worker.toml` when changing them.
4. Register the deployed Pages origin (for example, `https://likeback.pages.dev`) and its exact `/callback` URL in the X developer portal. Register custom domains or preview origins separately if used. Callback URLs and POST origin checks derive from the request URL, and shared links use the current page origin.
5. Check with `node --check src/worker.js` and `node --check public/_worker.js`. Preview locally with `wrangler pages dev public`; OAuth requires an HTTPS origin registered with X.

`wrangler.toml` is the Pages configuration; `wrangler.worker.toml` retains the Worker entry point and the same name, KV namespace ID, and AI binding. See Cloudflare's [Pages configuration](https://developers.cloudflare.com/pages/functions/wrangler-configuration/) and [Advanced Mode](https://developers.cloudflare.com/pages/functions/advanced-mode/) documentation.

`/login` performs no KV writes. PKCE verifier, state, and a ten-minute expiry live in an HMAC-signed HttpOnly Secure SameSite=Lax cookie, checked and cleared by the callback. Access tokens are checked before fetching the user. Login failures redirect to the landing page with a message; a successful re-login deletes the old session. Tokens remain in KV. Sessions have a server-checked absolute 30-day lifetime. Refresh begins five minutes before token expiry. X 400/401 during refresh or likes retrieval deletes the session, expires the cookie, and returns JSON 401; any frontend API 401 returns to login. Logout requires POST and a matching Origin.

## Privacy and retention

Server-side application storage contains exactly one kind of record: `sess:<random session ID>` in the SESSIONS KV namespace. It contains X access/refresh tokens, token expiry, absolute session expiry, and the signed-in user's profile (ID, name, username, and profile image URL). Its TTL is the remaining portion of the absolute 30-day login lifetime; refreshing tokens does not extend that lifetime. Logout, re-login, and invalid authentication remove session records.

No likes, post IDs, liked-post authors, media, category results, category overrides, rate-limit state, or summaries are written to KV, the Cache API, or other server-side application storage or logs. There is no aggregate summary cache. Old `likes:`, `stale:`, `cats:`, `cats:v2:`, `catov:`, `ratelimit:`, and `sum:` records are neither read nor modified or deleted by this version; their prior TTLs (if any) still apply. Removing existing records requires separate approval.

Each `/api/likes` and `/api/summary` request fetches X likes anew, using up to five sequential pages of 100, deduplicated and normalized only in request memory. There is no continuation beyond 500 posts. Later-page non-authentication errors may return current-request partial results. X 429 returns a friendly Japanese message, a JST retry time, `retryAt`, and a Retry-After header (at least 60 seconds when X provides no later reset). No server-side stale response is served and no browser response cache is implemented.

Rules classify every post during the request. If Workers AI is bound, one batch of at most 50 posts sends request-local indexes and up to 200 characters of text per post, with a three-second wait limit and rules as fallback. No IDs, author fields, or media are sent to classification AI. Summary AI receives only category shares and weekday/hour counts, also with a three-second wait limit. AI results are used only in the current request; no background work writes post data. An already submitted AI call may finish after the wait limit. Workers AI usage may incur charges under your account's plan.

Manual category overrides are stored only in this browser's localStorage as post ID/category pairs, scoped by signed-in account ID (`likeback:categories:<userId>`). They remain until browser site data is cleared. They are applied to displayed posts and never sent to the server; there is no `/api/category` endpoint. The server-generated personal summary uses fresh server classifications, without browser overrides. Theme preference also remains in browser localStorage. OAuth state and the PKCE verifier live in a signed HttpOnly browser cookie for ten minutes; the session cookie lasts at most 30 days.

KV is eventually consistent. Same-isolate token refresh work is shared and re-checks that the session exists before writing. KV cannot guarantee immediate global logout or cross-location serialization. No Durable Objects or rate-limit binding is used.

いいね順 preserves X's order; 人気順 sorts globally by like count; 新しい順 sorts by posting time and groups by JST date. X does not provide the time a post was liked. Rendering uses strict batches of at most 50 cards, lazy images, one fill loop, batched masonry measurements, and 200ms search debounce. Category changes update their card without redrawing the timeline.

`GET /api/summary` builds the personal card from loaded posts, with an empty-data fallback. Only aggregate category shares and weekday/hour counts go to summary AI: no post text, names, handles, authors, or user strings. Summary results are not persisted. The card labels time as よく見る投稿の投稿時間帯 and uses データなし when empty. Radar labels exclude zero-count categories. Save a 1200×630 PNG or open the X share composer; attach the image separately.

`GET /api/img?u=<encoded URL>` requires a valid session. It accepts HTTPS `pbs.twimg.com` profile_images, media, ext_tw_video_thumb, amplify_video_thumb, and tweet_video_thumb paths only, rejects redirects and images of 2 MiB or more, and has a five-second timeout including body reads. Image fetches bypass upstream caching, use request memory only, and return `Cache-Control: private, no-store`; the Cache API and KV are never used. Other responses use no-store. Production CSP hashes the inline script and excludes picsum; styles remain inline. HEAD is treated as GET without a response body; OPTIONS advertises each route's methods.

Open `mock.html` to preview fake posts using picsum.photos without backend calls. The production frontend permits picsum images only in mock mode. Mock changes remain local.

Run `node tools/render-sample.mjs` with a local X response in `data/likes.json`, or set `LIKES_INPUT` to its path. The renderer uses the first 500 posts and writes sample HTML to the OS temporary directory (`SAMPLE_HTML` overrides it). Add `--screenshot` to use Chrome with its sandbox enabled, writing `personal-card-sample-radar.png` beside this README (`SAMPLE_PNG` overrides it). Set `CHROME_BIN` to override the Chrome executable. Chrome must have the required local process/network permissions. Sample avatars use direct URLs; the preview is intended for screenshots rather than canvas PNG export.
