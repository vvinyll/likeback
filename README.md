# Xいいねビューア

A self-contained Cloudflare Worker (`mylikes`) with a Japanese frontend, 20 categories, month/category/author filters, search, shuffle, personal PNG cards, and responsive masonry (up to five columns). No build step or additional bindings are required.

1. Enable OAuth 2.0 for a confidential Web App in the X developer portal. Register `https://<worker-host>/callback` and your Worker origin. Request `tweet.read users.read like.read offline.access` and access to liked tweets.
2. Run `wrangler kv namespace create SESSIONS`. Replace the existing example namespace `id` in `wrangler.toml` with your own ID. The checked-in ID is an example value, not a usable placeholder or secret.
3. Configure `X_CLIENT_ID`, `X_CLIENT_SECRET`, and `SESSION_SECRET` using `wrangler secret put <NAME>`. Generate a long random session secret, for example with `openssl rand -hex 32`. Use OAuth 2.0 credentials, not OAuth 1.0 API keys. Keep the existing `SESSIONS` KV and `AI` bindings.
4. Run `node --check src/worker.js`, preview with `wrangler dev`, then deploy with `wrangler deploy`. OAuth needs HTTPS because cookies are Secure.

`/login` performs no KV writes. PKCE verifier, state, and a ten-minute expiry live in an HMAC-signed HttpOnly Secure SameSite=Lax cookie, checked and cleared by the callback. Access tokens are checked before fetching the user. Login failures redirect to the landing page with a message; a successful re-login deletes the old session. Tokens remain in KV. Sessions have a server-checked absolute 30-day lifetime. Refresh begins five minutes before token expiry. X 400/401 during refresh or likes retrieval deletes the session, expires the cookie, and returns JSON 401; any frontend API 401 returns to login. Logout requires POST and a matching Origin.

Likes are fetched in up to five sequential pages of 100, deduplicated, and normalized. The API returns `partial`, `hasMore`, `fetchedAt`, and `retryAt`; there is no continuation beyond 500 posts. The UI says 取得済みN件. Any later-page error returns gathered results as partial (authentication failures still invalidate the session). Fresh results use `likes:<userId>` for five minutes, partial results for one minute, and `stale:<userId>` for seven days. X reset/remaining and Retry-After headers control a `ratelimit:<userId>` negative cache with at least 60 seconds TTL. During limits, stale results are served with the retry time, or an empty partial result when no stale cache exists.

Rules and cached categories return immediately. Workers AI classification runs through `ctx.waitUntil` in batches of 50, sending only IDs and up to 200 characters per post. AI failures fall back to rules and are retried after a day. `cats:v2:<userId>` stores up to 1000 entries; partial retrieval does not prune absent IDs. AI results become visible on a subsequent API load. Workers AI usage may incur charges under your account's plan.

`POST /api/category` requires a session, matching Origin, and JSON `{id, category}` of at most 2048 bytes. IDs must be in cached likes; category must be one of the 20 categories, or null/empty to remove the override. `catov:<userId>` is capped at 1000 entries. Unchanged updates skip writes. Writes are throttled per user within a Worker isolate, and the latest map is re-read immediately before merging and writing. Overlapping updates receive 429; retry after a short pause.

KV is eventually consistent. Same-isolate likes/refresh/AI/summary work is shared; session refresh re-checks that the session exists before writing. These checks, throttles, and category merges are best-effort: KV cannot guarantee cross-location serialization, immediate global logout, single-use OAuth cookie consumption, or prevention of every lost update. No Durable Objects or rate-limit binding is used.

いいね順 preserves X's order; 人気順 sorts globally by like count; 新しい順 sorts by posting time and groups by JST date. X does not provide the time a post was liked. Rendering uses strict batches of at most 50 cards, lazy images, one fill loop, batched masonry measurements, and 200ms search debounce. Category changes update their card without redrawing the timeline.

`GET /api/summary` builds the personal card from loaded posts, with an empty-data fallback. Only aggregate category shares and weekday/hour counts go to summary AI: no post text, names, handles, authors, or user strings. The two-day `sum:` cache key includes user ID, JST date, and a hash of these statistics. The card labels time as よく見る投稿の投稿時間帯 and uses データなし when empty. Radar labels exclude zero-count categories. Save a 1200×630 PNG or open the X share composer; attach the image separately.

`GET /api/img?u=<encoded URL>` requires a valid session. It accepts HTTPS `pbs.twimg.com` profile_images, media, ext_tw_video_thumb, amplify_video_thumb, and tweet_video_thumb paths only, rejects redirects and images of 2 MiB or more, and has a five-second timeout including body reads. Successful responses use the edge cache via `caches.default` and `ctx.waitUntil`, with one-day cache headers. Other responses use no-store. Production CSP hashes the inline script and excludes picsum; styles remain inline. HEAD is treated as GET without a response body; OPTIONS advertises each route's methods.

Open `mock.html` to preview fake posts using picsum.photos without backend calls. The production frontend permits picsum images only in mock mode. Mock changes remain local.

Run `node tools/render-sample.mjs` with a local X response in `data/likes.json`, or set `LIKES_INPUT` to its path. The renderer uses the first 500 posts and writes sample HTML to the OS temporary directory (`SAMPLE_HTML` overrides it). Add `--screenshot` to use Chrome with its sandbox enabled, writing `personal-card-sample-radar.png` beside this README (`SAMPLE_PNG` overrides it). Set `CHROME_BIN` to override the Chrome executable. Chrome must have the required local process/network permissions. Sample avatars use direct URLs; the preview is intended for screenshots rather than canvas PNG export.
